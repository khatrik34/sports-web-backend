# Deploying the backend for free

Two paths, both costing nothing, both giving a **stable HTTPS URL** (better than a raw IP: browsers,
`next/fetch` caching and CORS all behave more predictably). You only need a real domain later for
branding — the free URL keeps working forever.

Pick one:

| | Path A — Render + free PostgreSQL | Path B — Oracle Cloud Always Free VM |
| --- | --- | --- |
| Cost | Free | Free, no expiry (card for identity check only) |
| Setup effort | ~15 min, no server admin | ~40 min, you own a Linux box |
| Sleeps when idle | **Yes** (~15 min), cold start 40–60 s | No |
| RAM | 512 MB | up to 24 GB (ARM) |
| Database | Neon / Supabase / Aiven free plan | PostgreSQL in Docker on the same VM |
| Best for | demo, showing the client | a site you actually depend on |

Both build the same `Dockerfile`; there is nothing Render- or Oracle-specific in the code.

---

## Path A — Render (API) + Neon (database)

Render's **free PostgreSQL expires**, so use a separate free Postgres. Neon's free plan (0.5 GB) is
enough for this schema; Supabase or Aiven work identically.

1. **Create the database.** On [neon.tech](https://neon.tech): new project → copy the connection
   details. You need:
   - host (looks like `ep-xxx-123456.eu-central-1.aws.neon.tech`)
   - database name, username, password
   - the JDBC URL ends up as:
     `jdbc:postgresql://<host>/<db>?sslmode=require&channelBinding=require`
     (drop `channelBinding` if your client library complains; `sslmode=require` is mandatory).
2. **Create the Render service.** Dashboard → **New → Blueprint** → connect
   `khatrik34/sports-web-backend` → Apply. Render reads `render.yaml` and asks for the values marked
   `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `DB_URL` | the JDBC URL from step 1 |
   | `DB_USERNAME` / `DB_PASSWORD` | from step 1 |
   | `APP_CORS_ALLOWED_ORIGINS` | e.g. `https://sports-web.vercel.app,https://sports-web-admin.vercel.app` |
   | `APP_PUBLIC_SITE_BASE_URL` | the deployed website URL |
   | `APP_BOOTSTRAP_ENABLED` | `true` (first deploy only) |
   | `APP_BOOTSTRAP_ADMIN_EMAIL` | your admin e-mail |
   | `APP_BOOTSTRAP_ADMIN_PASSWORD` | a strong password (12+ chars, mixed case, digit, symbol) |
   | `APP_BOOTSTRAP_ADMIN_DISPLAY_NAME` | `Administrator` |

   `APP_JWT_SECRET` is generated by Render and kept across deploys — do not regenerate it casually,
   that signs every staff user out.
3. **First deploy.** Flyway creates the schema and the bootstrap admin on startup. Then set
   `APP_BOOTSTRAP_ENABLED=false` (the bootstrap is idempotent, but leaving it on means a stale
   password in an env var that could re-create an account you deleted).
4. **Verify** (replace the host):

   ```bash
   curl -s https://sports-web-backend.onrender.com/actuator/health          # {"status":"UP"}
   curl -s "https://sports-web-backend.onrender.com/api/v1/public/news?size=1"
   curl -s -X POST https://sports-web-backend.onrender.com/api/v1/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"email":"<your admin email>","password":"<your password>"}'
   ```

   The login response carries `accessToken` and `user.mustChangePassword: true` if the bootstrap
   created it — that is the forced-change flow, so change the password before doing anything else.

**Free-tier caveat:** the service sleeps after ~15 minutes idle and the next request takes 40–60 s
(HTTP 502 for a few seconds while it wakes). For a demo that is fine; tell the website to render a
skeleton instead of erroring on the first slow response.

## Path B — Oracle Cloud Always Free VM (no sleeping)

1. Sign up at [cloud.oracle.com](https://cloud.oracle.com) (Always Free; card used for verification
   only). Create a **VM.Standard.A1.Flex** (ARM, 4 OCPU / 24 GB) with Ubuntu 22.04, and note the
   **public IP**. Open ingress for 80/443 (and 8080 while testing) in the subnet's security list
   **and** in the instance's firewall.
2. Install Docker:

   ```bash
   sudo apt update && sudo apt install -y docker.io docker-compose-v2 git
   sudo usermod -aG docker $USER && newgrp docker
   ```
3. Clone and configure:

   ```bash
   git clone https://github.com/khatrik34/sports-web-backend.git && cd sports-web-backend
   cp .env.example .env
   openssl rand -base64 48          # paste into APP_JWT_SECRET
   nano .env                        # DB_PASSWORD, APP_JWT_SECRET, CORS, base URL, bootstrap admin
   ```
4. Start it:

   ```bash
   docker compose up -d --build
   docker compose ps                # both services healthy
   curl -s localhost:8080/actuator/health
   ```

   From outside: `http://<public-ip>:8080/actuator/health`. That is the "runs on an IP" stage you
   asked about — no domain needed.
5. When you buy a domain, add an `A` record to the public IP and put Caddy or Nginx in front for
   HTTPS (Caddy is two lines: `caddy reverse-proxy --from api.example.com --to 127.0.0.1:8080`).
   Nothing in the app changes — just set `APP_PUBLIC_SITE_BASE_URL` to the final https site URL.

## Environment variables that matter

| Variable | Required | Notes |
| --- | --- | --- |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | yes | `?sslmode=require` for managed Postgres |
| `APP_JWT_SECRET` | yes | Base64, ≥32 bytes decoded (`openssl rand -base64 48`). No default; the app refuses to start without it |
| `APP_CORS_ALLOWED_ORIGINS` | yes for browser clients | comma separated origins of the website and admin panel |
| `APP_PUBLIC_SITE_BASE_URL` | yes | used for canonical URLs and sitemaps |
| `SERVER_PORT` | on Render | Render sets `PORT=10000`; set `SERVER_PORT=10000` to match |
| `APP_DOCS_PUBLIC` | no (default `false`) | keep Swagger closed on a public host |
| `APP_BOOTSTRAP_*` | first deploy only | creates the first SUPER_ADMIN; idempotent, then disable |
| `JAVA_OPTS` | no | free instances: `-XX:MaxRAMPercentage=70 -XX:+UseSerialGC` |

## Common failures

| Symptom | Cause |
| --- | --- |
| Container exits, log says `JWT secret must be configured` | `APP_JWT_SECRET` missing/too short |
| `Flyway validate failed` | someone changed a migration that already ran — never edit applied migrations; add a new `V<n>__` file |
| `Connection refused` / `SSL off` from Neon | missing `?sslmode=require` in `DB_URL` |
| Deploy "unhealthy" on Render | the app bound to 8080 while Render routes to `PORT` — set `SERVER_PORT=10000` |
| OOM kill on a 512 MB instance | raise `-XX:MaxRAMPercentage` is wrong direction — lower it to 65 and keep `UseSerialGC` |
| First request of the day takes ~1 minute | free instance cold start (Path A only), expected |

## Demo content (optional)

An empty database means empty public pages. For a demo, load the ready-made dataset:

```bash
# docker compose (Path B): add to .env, then restart the app container
APP_FLYWAY_LOCATIONS=classpath:db/migration,classpath:db/demo
docker compose up -d --build

# Render (Path A): same value as an environment variable
SPRING_FLYWAY_LOCATIONS=classpath:db/migration,classpath:db/demo
```

It arrives as the repeatable Flyway migration `R__demo_data` from `db/demo` and contains: 4 international teams, 12 players,
Asia Cup 2026 with a points table, three fixtures (one `LIVE`, one `COMPLETED` with a full scorecard and
commentary, one `SCHEDULED`), 5 published articles in 2 categories, 3 videos, 5 homepage sections and one
legacy-URL redirect. Fixed UUIDs plus `ON CONFLICT DO NOTHING` mean it can never duplicate rows, and it
creates **no user accounts** — the first admin still comes from `app.bootstrap`.

To run later without the demo data, remove the extra location from the variable (Flyway records `R__demo_data` in `flyway_schema_history`; removing the folder afterwards is
safe, the rows simply stay).

## What this repository does **not** do for you

- It does not run a deployment: no CI image build yet (the CI runner has no Docker), so Render builds
  from the `Dockerfile` itself and the VM builds with `docker compose up --build`.
- It does not seed demo content. Empty database means empty public pages — enter news, teams, fixtures
  and homepage sections through the admin panel, or ask for a seed script.
